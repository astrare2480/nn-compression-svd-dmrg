# srcアーキテクチャ設計

## 1. 目的

`src/nn_compression/` は、Notebookで検証したニューラルネットワーク圧縮処理を、再利用可能な実装として整理するためのパッケージである。

このリポジトリでは圧縮手法を、

```text
SVD
→ Tucker / HOSVD / HOOI
→ TT / MPS
→ DMRG-like optimization
```

の順に段階的に追加する。

そのためsrcは、特定のNotebookや特定の圧縮方式へ密結合させず、**数学操作・圧縮アルゴリズム・学習評価・実験支援を責務ごとに分離する**。

Core API v1ではSVD〜Tucker/HOOIまでの既存Public APIを安定化し、TT/MPS・DMRG追加時には既存APIの意味を変更するより新規API追加を優先する。

---

## 2. 全体構成

Notebook / Experimentが各責務のPublic APIを組み合わせる。

```text
Notebook / Experiment
   ├─→ compression
   ├─→ training
   ├─→ metrics
   ├─→ selection
   ├─→ datasets
   └─→ models / utils

compression
   ├─→ tensor
   ├─→ utils
   └─→ metrics

metrics
   ├─→ training
   └─→ utils

datasets
   └─→ utils

models / selection / tensor / training / utils
   → 基本的に上位圧縮方式へ依存しない
```

**矢印は「利用する側 → 依存先」**を表す。

現状、HOOIの再構成誤差計算のため、

```text
compression.hooi
→ metrics.relative_frobenius_error
```

という依存がある。またmodel比較側では、

```text
metrics.model_comparison
→ training.loops
```

として `evaluate` とtraining-state保存helperを利用する。

このため `metrics → compression` の逆依存は追加しない。validation helperの重複を単純にDRY化しない理由もここにある。

## 3. Notebookとsrcの責務分離

### Notebook

Notebookには、学習・検証過程として意味のあるものを残す。

```text
数式
shape確認
途中結果
実験固有rank候補
グラフ・表
結果解釈
```

### src

srcには、複数Notebookから再利用する処理を置く。

```text
Tensor演算
SVD / Tucker / HOOI
Module置換
学習・評価ループ
共通metrics
seed / path / named module操作
```

### srcへ入れないもの

実験固有の値はsrcへ固定しない。

例：

```text
CIFAR-10 Tuckerの最終rank=(32,16)
特定NotebookのCSV名
特定runのaccuracy
```

これらはNotebook/results/docs側の責務である。

## 4. 主要コンポーネント

### `tensor`

分解手法に依存しないmode-nテンソル演算を提供する。

```text
unfold
fold
mode_dot
```

Tucker専用層ではなく、将来のTensor Network実装からも利用可能な下位層とする。

### `compression`

低rank分解とNN層への変換を担当する。

```text
SVD
Linear / Conv2d factorization
HOSVD
HOOI
Tucker-2 Conv
named layer replacement
rank sweep
```

Tensor-level decompositionとModule constructionを分離する。

### `training`

圧縮方式に依存しない学習・評価処理を担当する。

```text
train_one_epoch
evaluate
fit_with_early_stopping
```

### `metrics`

圧縮結果を比較するための指標と理論計算量を担当する。

```text
parameters
accuracy drop
agreement
logits RMSE
latency
MACs
relative Frobenius error
```

### `selection`

rank候補等の実験結果からPareto frontier・kneeを抽出する。

### `models` / `datasets`

既存実験を再現するためのbaseline modelとDataset/DataLoader構築を提供する。

### `utils`

seed、path、named module操作等の圧縮方式に依存しない共通処理を提供する。

## 5. 設計上の主要境界

### 5.1 数学表現とPyTorch Module

例：Tucker-2。

```text
weight Tensor
   ↓
tucker2_decompose_conv_weight / tucker2_hooi
   ↓
core / factors
   ↓
build_tucker2_conv_from_components
   ↓
nn.Sequential
```

この境界により、

- 分解アルゴリズムだけを比較できる
- HOSVDとHOOIで同じModule builderを使える
- Tensor-level APIではautograd graphを保持できる
- Module構築では元Parameterから独立したleaf Parameterを作れる

という役割分担を保つ。

### 5.2 圧縮と評価

圧縮アルゴリズムはaccuracyやlatencyの評価方法を持たない。

```text
compression
→ 圧縮モデル / factorsを生成

metrics
→ 結果を測定

training
→ Fine-tuning
```

と分ける。

### 5.3 generic APIとexperiment-support API

```text
truncated_svd / hosvd / hooi
→ generic core API

make_two_layer_svd_model / estimate_mlp_macs
→ 既存実験向けsupport API
```

実験支援関数を万能化して数学コアへ混ぜない。

---

## 6. 非破壊性

モデル圧縮ではbaseline modelを原則変更しない。

```text
baseline
   ↓ deepcopy
compressed copy
   ↓ layer replacement
compressed model
```

Fine-tuning後もbaselineとcompressedでParameter object / storageを共有しない。

層単体APIも入力layerそのものを変更せず、新しいModuleを返す。

---

## 7. 状態とautograd

### 評価時状態

`evaluate`、model comparison、benchmarkは一時的に `eval()` を使うが、終了後にrootだけでなく**全submoduleのtraining状態を復元**する。

### Tensor-level decomposition

必要な場合に計算graphを維持できるよう、Tensor-level Tucker/HOOI APIでは不用意にdetachしない。

### Module construction

学習済みweightから新しいParameterを初期化する時点でgraphを切り、新しいleaf ParameterとしてFine-tuningする。

---

## 8. 拡張方針

TT/MPS追加時は、

```text
既存SVD/Tucker APIをTTにも対応させる
```

のではなく、

```text
既存tensor / training / metrics / utilsを再利用
+
TT/MPS固有APIを追加
```

とする。

同様にDMRG-like optimizationは `hooi_sweep()` の意味を拡張せず、DMRG専用のlocal update / sweep APIを追加する。
