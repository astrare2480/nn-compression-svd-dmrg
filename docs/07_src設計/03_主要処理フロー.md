# 主要処理フロー

## 1. 目的

このファイルは、`src/nn_compression/` のPublic APIが**実験の中でどう接続されるか**を示す。

関数単体の仕様ではなく、データとmodelがどの順に流れるかを設計として固定する。

---

## 2. Linear SVD圧縮

```text
nn.Linear
   │
   │ weight
   ▼
truncated_svd
   │
   ├─ U_r
   ├─ S_r
   └─ Vh_r
   │
   ▼
factorize_linear_layer
   │
   ▼
Linear(in → r)
   ↓
Linear(r → out)
```

### 利用フロー

```text
baseline model
→ 対象Linearのrankを決める
→ factorize_named_linear / factorize_named_layers
→ compressed model
→ evaluate
→ collect_compression_metrics
→ 必要ならFine-tuning
```

### 設計ポイント

- baseline modelは変更しない
- factorized layerは新しいParameterを持つ
- biasは最終Linearへ置く
- rank選択と分解処理を分離する

---

## 3. Conv2d SVD圧縮

```text
Conv2d weight
(C_out, C_in, kH, kW)
        │
        ▼
conv2d_weight_matrix
        │
        ▼
(C_out, C_in*kH*kW)
        │
        ▼
truncated_svd
        │
        ▼
factorize_conv2d_layer
        │
        ▼
Conv(C_in → r, kH×kW)
        ↓
Conv(r → C_out, 1×1)
```

### 評価

```text
compressed model
├─ parameters
├─ validation accuracy
├─ agreement
├─ logits RMSE
├─ theoretical MACs
└─ measured latency
```

MACsとlatencyは別指標として扱う。

---

## 4. SVD rank sweep

```text
rank candidates
      │
      ▼
sweep_layer_ranks / sweep_conv2d_ranks
      │
      ├─ baseline modelからdeepcopy
      ├─ 対象layerだけ置換
      ├─ validation evaluation
      ├─ parameters
      ├─ MACs
      ├─ agreement / RMSE
      └─ latency
      │
      ▼
list[dict]
      │
      ▼
DataFrame
      │
      ├─ Pareto frontier
      └─ knee selection
```

rank sweepはcandidateを測定するだけで、最終rankを自動的に「正解」として決定する責務は持たない。

---

## 5. HOSVD

```text
Tensor X
   │
   ├─ unfold(X, mode 0) → truncated_svd → U0
   ├─ unfold(X, mode 1) → truncated_svd → U1
   └─ ...
   │
   ▼
元Xへ各factorの転置をmode_dot
   │
   ▼
core G
```

### 重要な設計判断

factorは各modeについて**元のXから独立に求める**。

```text
正しいHOSVD設計
X → U0
X → U1
X → U2

採用しない設計
X → U0 → projected core → U1 → ...
```

後者へ変更すると別アルゴリズムになるため、Core API v1では変更しない。

---

## 6. HOOI

```text
X + ranks
   │
   ▼
HOSVD initialization
   │
   ├─ core
   ├─ factors
   └─ initial error → history[0]
   │
   ▼
hooi_sweep
   │
   ├─ target mode以外をproject
   ├─ unfold
   ├─ SVD
   └─ factor更新
   │
   ▼
core_from_factors
   │
   ▼
reconstruct_tucker
   │
   ▼
relative_frobenius_error
   │
   ▼
has_converged
   │
   ├─ false → next sweep
   └─ true  → finish
```

### 更新順

`ranks` Mappingの挿入順を使用する。

Tucker-2では通常、

```python
{0: rank_out, 1: rank_in}
```

なのでmode 0 → mode 1の順に更新する。

---

## 7. Tucker-2 Conv / HOSVD

Conv2d weight：

```text
W = (C_out, C_in, kH, kW)
```

channel mode 0 / 1だけを圧縮する。

```text
W
 ↓
tucker2_decompose_conv_weight
 ↓
core, U_out, U_in
 ↓
build_tucker2_conv_from_components
 ↓
input projection  1×1
 ↓
core convolution  kH×kW
 ↓
output projection 1×1
```

### Module構造

```text
C_in
 → R_in
 → R_out
 → C_out
```

空間kernelはcore convolutionへ残す。

---

## 8. Tucker-2 Conv / HOOI

```text
conv.weight
   │
   ▼
tucker2_hooi
   │
   ├─ HOSVD initialization
   ├─ iterative HOOI
   └─ core / factors / history
   │
   ▼
build_tucker2_conv_from_components
   │
   ▼
3-layer Conv module
```

HOSVDとHOOIは**分解方法だけが異なり、Module constructionは共有**する。

これにより同rank・同構造で分解方法だけを比較できる。

---

## 9. Fine-tuning

```text
compressed model
   │
   ▼
fit_with_early_stopping
   │
   ├─ train_one_epoch
   ├─ evaluate(validation)
   ├─ best state保存
   └─ patience判定
   │
   ▼
best validation state restore
   │
   ▼
test evaluation
```

### train metric

shuffle付きtraining loaderを評価目的で再走査すると、専用Generatorの状態を進める可能性がある。

そのため、

```text
train_loader
→ 学習専用

train_eval_loader
→ shuffle=Falseでtraining metric取得
```

を基本とする。

---

## 10. モデル比較

```text
baseline model ─────┐
                    ├─ evaluate
compressed model ───┘
                    ├─ parameter reduction
                    ├─ agreement
                    ├─ logits RMSE
                    ├─ MACs
                    └─ benchmark
```

### benchmark

baselineとcompressedでは同じ `input_batch` を利用する。

```text
same input
same warmup
same repeats
```

を揃え、model差以外をできるだけ測定条件へ混ぜない。

---

## 11. Fine-tuning後Tucker weight評価

Tucker-2 ModuleをFine-tuningした後、元のConv weightとの距離を見る場合：

```text
3-layer Tucker-2 module
   │
   ▼
tucker2_effective_weight
   │
   ▼
effective 4D weight
   │
   ▼
relative_frobenius_error(original, effective)
```

`tucker2_effective_weight()` は評価utilityであり、この再構成経路を使ったgradient計算を目的としない。

---

## 12. TT/MPSへ進むとき

既存フローのうち、

```text
training
evaluation
model comparison
benchmark
seed/path
```

は再利用する。

一方、

```text
TT-SVD
tensorization
TT cores
bond rank
TT reconstruction
```

は新しいcompressionフローとして追加する。

既存HOSVD/HOOIフローをTT向けに変形しない。
