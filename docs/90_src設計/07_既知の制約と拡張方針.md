# 既知の制約と拡張方針

## 1. 目的

Core API v1は「現在のsrcが完全に一般化されている」という意味ではない。

既存SVD/Tucker実験を安定化した時点のcontractを固定し、未対応範囲は明示したうえでTT/MPS・DMRGへ進む。

このファイルでは、

```text
仕様として意図的に制限しているもの
技術的負債として残しているもの
将来拡張時に壊してはいけないもの
```

を整理する。

---

## 2. Tucker/HOOIのdtype対応範囲

現行HOSVD/HOOIの正式対応範囲は**実数浮動小数点Tensor**。

```text
float32 / float64等
→ supported

complex
integer
bool
→ decomposition APIではTypeError
```

複素Tensorではfactor射影に共役転置 `U.mH` が必要になるため、単にcomplex guardを外して対応したことにはしない。

複素対応が必要になった場合は、

- transpose / conjugate transpose
- reconstruction
- HOOI projection
- full-rank regression

をまとめて設計・テストする。

TT/MPSで複素対応を導入する場合も、既存Tucker APIだけ片側で意味を変えず、リポジトリ全体のdtype policyとして検討する。

---

## 3. NumPy scalar受理方針は完全統一していない

整数入力の扱いはAPIごとに少し異なる。

```text
SVD rank / max_iter
→ operator.index
→ NumPy integer scalar受理
→ Tensor scalar拒否

MACs rank / output size
benchmark warmup / repeats
→ operator.index
→ Python bool / Tensor scalar拒否

mode validation
→ Python int中心
```

Core API v1では、この違いを一括refactorするためだけに既存APIを変更しない。

将来統一する場合は、

```text
Python intのみ
or
__index__対応scalarまで
```

のどちらを標準にするか先に決め、contract testを追加してから行う。

---

## 4. validation helperが複数箇所に存在する

似たprivate validationが、

```text
tensor/validation.py
compression/tucker_validation.py
compression/svd.py
metrics/macs.py
metrics/model_comparison.py
```

に分散している。

`compression.hooi → metrics` という依存があるため、metricsからcompression helperをimportすると循環importになりやすい。

将来整理する場合は、依存グラフの下位にneutralなvalidation moduleを置く等、方向を決めてから共通化する。

単純なDRY化のために循環依存を導入しない。

---

## 5. `collect_compression_metrics` は再走査可能loaderを前提とする

内部で同じloaderを複数回使う。

```text
evaluate
agreement
logits_rmse
```

通常のDataLoaderのようなre-iterable objectを前提とし、one-shot iteratorの自動cacheは行わない。

必要になった場合は、

- 1 passで複数metricsを集計する
- batchをcacheする
- iterator factoryを受ける

等を別途設計する。

---

## 6. `non_shuffling_loader` は任意DataLoaderの完全cloneではない

一般的なDataLoader設定を引き継いで `shuffle=False` loaderを作るが、custom sampler / custom batch_sampler / 特殊subclassを完全再現するcontractではない。

既存実験の標準DataLoaderでの利用を主目的とする。

---

## 7. `take_inference_batch` のsampler判定

標準のshuffle付きDataLoaderで使われる `RandomSampler` は明示的に拒否する。

独自samplerが乱数状態を消費するかどうかまで自動判定するAPIではない。

custom samplerでは `input_batch` を明示的に渡すのを推奨する。

---

## 8. model-specific helperは意図的に残す

以下はgeneric library coreではなく、既存Notebook再現用のExperiment Support API。

```text
make_one_layer_svd_model
make_two_layer_svd_model
estimate_mlp_macs
estimate_cnn_linear_macs
Fashion-MNIST dataset helpers
```

TT/MPS対応のためにこれらを万能化しない。

必要なgeneric APIは別に追加する。

---

## 9. model architectureは実験fixtureとして固定する

`MNISTMLP`、`FashionMNISTCNN`、`CIFAR10CNN` の主要layer名・default architectureはcheckpoint、named compression、Notebook、resultsと結びついている。

Core API v1中は不用意に変更しない。

新architectureが必要なら新classまたは明示的な新optionを追加する。

---

## 10. path utilityは `.git` をproject root markerにする

`find_project_root()` は `.git` が存在するdirectoryをproject rootとする。

`.git` を含まないzip展開等ではroot検出できない。

必要なら将来、

```text
pyproject.toml
環境変数
explicit project_root
```

等を別仕様として検討する。

---

## 11. MACsは理論値でありlatencyではない

既存MACsは主要な積和演算数を見積もる。

含まれないもの：

```text
bias addition
activation
memory transfer
kernel launch overhead
framework overhead
```

したがって、

```text
MACs reduction != latency reduction
```

を前提とする。

TT/MPSでも理論演算量と実測latencyを分ける。

---

## 12. `fit_with_early_stopping` のscalar validation

`max_epochs / patience / min_delta` はHOOI/benchmarkほど厳格な統一validation helperを持たない。

現在はExperiment Support APIとしてsignature・return structure・Early Stopping semanticsを固定し、全面的なscalar policy統一は別課題とする。

---

## 13. Core API v1 self reviewで解消したgap

freeze前のself reviewで次を修正した。

### Conv MACs output size

`conv2d_macs / compressed_conv2d_macs / estimate_conv2d_macs` の出力空間sizeを、bool/Tensor scalarを拒否する正の整数scalarへ統一。

### MACs rank / benchmark count

`compressed_*_macs`のrankと`benchmark_inference`の`warmup/repeats`でTensor scalarを明示拒否し、SVD側のinteger policyに近づけた。

### Tucker standalone utility ndim

`reconstruct_tucker(core,{})` と `core_from_factors(X,{})` でも2階以上を要求するよう統一。

### Tucker/HOOI dtype

複素数だけでなくinteger/bool TensorもPublic API境界で拒否し、実数浮動小数点Tensorを正式対応範囲とした。

### Tucker-2 rank説明

component shape制約とdecomposition時のmode-unfolding feasibilityを分けて設計書へ記載。

これらは中心アルゴリズムの変更ではなく、Public API境界の明確化である。

## 15. TT/MPS基礎APIの現在地

Notebook 00〜13から、再利用可能な基礎処理を次のcomponentへsrc化した。

```text
tt.py
→ TT-SVD / error bound / reconstruction / physical shape / rank / parameter count

tt_validation.py
→ core chain / pair compatibility

tt_canonical.py
→ mixed-canonical form / center move / canonicality diagnostics

tt_rounding.py
→ bond singular values / single-bond truncation / TT-rounding

tt_contraction.py
→ inner product / Frobenius norm
```

既存`hosvd / hooi`の意味はTT向けに変更していない。TT-matrix、TT-Linear、NN層置換は後続機能とする。

### 15.1 対応dtypeと入力表現

TTの分解、正準化、rounding、contractionは`torch.float32`と`torch.float64`を正式対応範囲とする。complex、integer、bool、CPU上でSVD/QR対応が限定される`float16 / bfloat16`は拒否する。

TT coreは各siteでshape $(r_{k-1},n_k,r_k)$、左右境界rank 1、隣接bond一致、全coreのdtype/device一致を要求する。2項演算ではorder、物理次元、dtype、deviceの一致を要求するが、A/Bのbond rankは異なってよい。

### 15.2 canonicalization / roundingのdynamic range

`tt_canonicalize`と、それを前処理に使う`tt_bond_singular_values` / `tt_truncate_bond` / `tt_round`は、入力dtypeのままQRと余りの隣接coreへの吸収を行う。

coreごとのscaleが極端に不均衡なgaugeでは、最終dense Tensorが表現可能でも、中間演算がoverflow / underflowし得る。例えばfloat32のrank-1 TTでcore scaleが`1e30`, `1e-30`, `1e-30`の場合、right-to-left処理中の積が0へunderflowする可能性がある。

したがって、通常の正準化済みまたはscale-balancedなTTを対象とし、任意dynamic rangeへのscale-invariant性は保証しない。

`tt_canonicality_errors`の最終normは最大絶対値で正規化して計算するため、Gram差として残った表現可能な微小値を二乗underflowで0にしない。ただしGram行列`M.mT @ M`または`N @ N.mT`を作る段階の丸め・overflow / underflowまでは補償しない。

### 15.3 rounding診断値

rank選択は非二乗の局所予算`delta`とtail normを比較し、`math.hypot`を用いる。これは極小・極大値の二乗underflow / overflowがrank選択へ影響することを避けるためである。

一方、報告用の`local_tail_sq` / `discarded_tail_sq`は最後にPython floatで二乗する。この値だけは極端な範囲で0または`inf`になり得る。その場合は非二乗の`local_error`、`global_error_estimate`、実測再構成誤差を優先する。

`tt_svd_error_bound`も逐次SVDの局所tail normとその全体合成をscale-safeに計算する。指定rankだけでなく`torch.linalg.matrix_rank`による数値rankの切り詰めを反映するため、元Tensorのcut unfoldingだけから求める教科書上のtail列とは意味が異なる。SVDと数値rank判定そのものの丸め誤差は残るため、上限値は厳密解析値ではなく現行実装に対応する数値的な上限である。

### 15.4 contractionのscale制約

`tt_inner`はleft environmentを直接更新し、明示的な$O(nr^4)$中間Tensorやdense Tensorを作らない。ただしcore scaleの自動補正は行わないため、極端な値では`einsum`中間積がoverflow / underflowし、`inf`、`0`、`NaN`が現れ得る。

`tt_fro_norm`は正値で通常の平方根と一致し、零点ではforward 0・有限な0勾配を返す。有限負値と`-inf`は`ValueError`、`NaN`は隠さず伝播する。負値判定の`.item()`によりCUDA同期が発生する。

### 15.5 TT距離APIの延期

`tt_distance_sq` / `tt_distance`はCore API v1へ含めない。これまで検討した方式では、次の品質条件を同時に満たせなかった。

```text
偏極恒等式
→ 近接した大規模TTで桁落ち

direct-sum + QR
→ QR前の大きいcoreで精度を失い、rank落ちではNaN gradient

site差のtelescoping / 部分空間式
→ 対称性、複数site差、異rankで数値上の問題

double-doubleと特殊経路
→ overflow / underflow、誤ったautograd、過大な一時メモリ
```

不正な実装をprivate helperとして残さず、距離APIと専用helperは削除した。`tt_inner`の結果を呼び出し側で

$$
\|A-B\|_F^2
=
\langle A,A\rangle
+
\langle B,B\rangle
-
2\langle A,B\rangle
$$

へ代入する方法も、近接・大規模TTの安定な距離APIとしては推奨しない。

再導入前に、次を独立に設計・検証する。

```text
共通の直交基底またはgauge固定
rank-deficient coreでもbackwardが有限な正準化
bond rankを制御したTT加減算
対称性とA-A=0のforward / gradient
全core位置の近接摂動と異rank
O(nr^3)級の計算量と一時メモリ
```

真値が誤差床より小さいgauge違いのケースを、実装自身の計算経路をoracleにせず、denseまたは高精度参照で検証できることも再導入条件とする。

## 16. DMRG追加方針

DMRG-like optimizationはHOOIと概念的に、

```text
initialization
→ local update
→ sweep
→ convergence
```

でつながるが、`hooi_sweep()` を万能sweepへ変更しない。

DMRG固有の、

```text
MPS/TT representation
local problem
environment
left/right sweep
truncation
convergence
```

を新しい責務として追加する。

---

## 17. breaking changeが必要な場合

最低限、

```text
1. 変更理由
2. 影響Public API
3. Notebookへの影響
4. migration方法
5. contract test更新
6. 設計書更新
```

を残す。

可能なら旧APIをcompatibility wrapperとして一定期間維持する。

---

## 18. Core API v1確定条件

```text
Public API一覧と__all__が一致
現行srcとsignatureが一致
contract testと設計書が一致
既存ノートと矛盾しない
freeze前のcontract gapが残っていない
self review後の全pytestがgreen
git diff --checkがclean
```

テスト実行確認が終わるまでは、設計・静的contract review完了、最終freeze待ちとする。
