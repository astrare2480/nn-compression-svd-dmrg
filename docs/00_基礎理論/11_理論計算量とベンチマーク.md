# 理論計算量と実測時間

## サマリー

SVD圧縮では、次の3つのコストを分ける。

1. モデルに保存するパラメータ数
2. 圧縮後forwardの理論演算回数
3. 実際の推論時間

さらに、学習済み重みにSVDを1回かける前処理コストも別に存在する。

```text
SVDを計算する時間
≠
圧縮後モデルを推論する時間
```

NN圧縮の主目的が推論モデルの軽量化なら、報告すべき中心は、

- 圧縮後パラメータ数
- 圧縮後MACs
- 圧縮後実測latency

である。

SVD処理時間は、圧縮を何回実施するか、モデルを何回推論するかによって重要度が変わる。

## 1. 元Linear層のパラメータ数

```python
nn.Linear(
    in_features=D_in,
    out_features=D_out,
    bias=True,
)
```

の重み数は、

$$
D_{\mathrm{out}}D_{\mathrm{in}}
$$

bias数は、

$$
D_{\mathrm{out}}
$$

である。

総パラメータ数は、

$$
P_{\mathrm{original}}
=
D_{\mathrm{out}}D_{\mathrm{in}}
+
D_{\mathrm{out}}
$$

となる。

---

## 2. 低ランク2層のパラメータ数

前段：

```text
Linear(D_in, r, bias=False)
```

後段：

```text
Linear(r, D_out, bias=True)
```

なので、

$$
P_{\mathrm{lowrank}}
=
rD_{\mathrm{in}}
+
rD_{\mathrm{out}}
+
D_{\mathrm{out}}
$$

である。

bias数は元と同じため、圧縮成立条件では相殺される。

$$
P_{\mathrm{lowrank}}
<
P_{\mathrm{original}}
$$

より、

$$
r
<
\frac{
D_{\mathrm{in}}D_{\mathrm{out}}
}{
D_{\mathrm{in}}+D_{\mathrm{out}}
}
$$

となる。

## 3. rank上限と圧縮成立rank

| 層 | shape | 数学的最大rank | パラメータが減るrank |
|---|---:|---:|---:|
| `fc1` | 512×784 | 512 | 309以下 |
| `fc2` | 256×512 | 256 | 170以下 |
| `fc3` | 10×256 | 10 | 9以下 |

### `fc3` の重要点

`fc3` ではrank 10はSVDとして有効である。

しかし、

```text
元のパラメータ数      = 2,570
rank 10の2層化       = 2,670
```

となり、100個増える。

したがって、最大rankと圧縮になるrankは別である。

## 7. 元Linear層のMACs

1サンプルに対する、

```text
Linear(D_in, D_out)
```

の乗算加算回数、MACsは概ね、

$$
\operatorname{MACs}_{\mathrm{original}}
=
D_{\mathrm{in}}D_{\mathrm{out}}
$$

である。

bias加算は別途存在するが、主要な行列積と比べて小さいため、最初の比較では除外してよい。

---

## 8. 低ランク2層のMACs

前段：

$$
D_{\mathrm{in}}r
$$

後段：

$$
rD_{\mathrm{out}}
$$

合計：

$$
\operatorname{MACs}_{\mathrm{lowrank}}
=
r
\left(
D_{\mathrm{in}}
+
D_{\mathrm{out}}
\right)
$$

圧縮成立条件と同じ形になる。

### batch size $N$

バッチ全体では、

$$
N
D_{\mathrm{in}}D_{\mathrm{out}}
$$

および、

$$
N
r
\left(
D_{\mathrm{in}}
+
D_{\mathrm{out}}
\right)
$$

となる。

---

## 9. MACsとFLOPs

1 MACを、

```text
1回の乗算 + 1回の加算
```

と数える場合、2 FLOPsとする流儀がある。

$$
\operatorname{FLOPs}
\approx
2\times\operatorname{MACs}
$$

一方、資料によってはMACを1演算として報告する。

比較では、

- MACsなのか
- FLOPsなのか
- bias加算を含むか
- activationを含むか

を明記する。

このノートでは、Linear層の主な行列積をMACsで比較する。

---

## 10. パラメータ数とMACsが似た式になる理由

密なLinear層では、各weightが1回のforwardで概ね1回使われる。

そのため、1サンプル当たりでは、

```text
重み数
≈
乗算回数
```

となる。

しかし実測時間は、重み数やMACsだけで決まらない。

---

---

## 10.1 パラメータ数削減とMACs削減が一致する特殊ケース

Linear層だけを2因子へ置換し、bias総数が圧縮前後で変わらない場合、モデル全体について、

```text
parameters = MACs + bias総数
```

となることがある。
このとき、

```text
parameters < baseline_parameters
```

と

```text
compute_reduction > 0
```

は数学的に同じ候補集合を表す。

ただし、これは一般則ではない。
畳み込み、BatchNorm、Embedding、追加bias、非線形層、その他の構造が入れば同値とは限らない。

Fashion-MNISTの `784 -> 512 -> 256 -> 10` MLPでは、圧縮前後でbias総数が778のままなので、この等価性が成立した。

---

## 11. パラメータ数が減っても必ず速くならない理由

元の1回の大きな行列積が、2回の小さい行列積へ変わる。

実測時間には、次が影響する。

- kernel起動回数
- 小行列のGPU利用効率
- メモリアクセス
- batch size
- CPUのBLAS実装
- GPUの種類
- dtype
- Python overhead
- cache
- 非同期実行
- 他の層の割合

小さいMNIST MLPでは、理論MACsが減っても、2層化のオーバーヘッドで速くならない可能性がある。

この結果自体も重要な実験結果である。

---

## 12. SVD自体の計算コスト

SVDは無料ではない。

$m\times n$ 行列のSVDには、概ね大きな前処理コストがかかる。

ただしpost-training圧縮では、通常、

```text
学習後に1回SVD
↓
圧縮モデルを多数回推論
```

となる。

この場合、SVD時間は一度だけ支払うオフラインコストである。

### 分けて記録する

- `svd_decomposition_time_ms`
- `inference_latency_ms`

を別列にする。

SVD時間をforward latencyへ含めない。

---

## 13. 実測時間の対象

少なくとも次の2種類を分ける。

### 1バッチlatency

決めたbatch sizeの入力を1回forwardする時間。

### 1サンプル換算

$$
\frac{
\text{batch latency}
}{
\text{batch size}
}
$$

ただし、batch処理は完全な線形スケールではないので、batch sizeも必ず併記する。

### dataset throughput

$$
\frac{
\text{処理サンプル数}
}{
\text{総時間}
}
$$

としてsamples/sを出す。

## 14. ベンチマーク前の条件

- `model.eval()`
- `torch.no_grad()` または `torch.inference_mode()`
- 同じdevice
- 同じdtype
- 同じinput shape
- 同じbatch size
- 同じ回数
- DataLoader時間を含むか明記

純粋なmodel forwardを測るなら、入力Tensorを事前にdeviceへ置き、DataLoaderと転送時間を除外する。

エンドツーエンド性能を測るなら、DataLoaderや転送も含む別測定にする。

## 15. warm-up

初回実行には、

- CUDA context初期化
- kernel選択
- memory allocation
- cache

などが含まれる。

そのため、計測前に複数回forwardを実行する。

```text
warm-up 10〜50回
measurement 100回以上
```

は小さいモデルの初期目安である。

実際の回数は環境に応じて調整する。

---

## 16. CUDA同期

CUDA演算は非同期である。

Python側の時計だけを見ると、GPU処理が完了する前に時間を取得する可能性がある。

計測の前後で、

```python
torch.cuda.synchronize()
```

を呼ぶ。

またはCUDA Eventを使う。

CPU測定では同期は不要である。

---

## 17. 平均より中央値も記録する

latencyは、OS割り込みや他プロセスによって外れ値を含む。

記録候補：

- mean
- median
- standard deviation
- minimum
- p90
- p95

最初は、

```text
median latency
mean latency
```

を記録すればよい。

## 18. CPUとGPUを分ける

CPUとGPUでは、最適なrankやbatch sizeが異なる可能性がある。

### CPU

- 小さいモデルでも比較しやすい
- スレッド数の影響が大きい
- BLAS実装の影響がある

### GPU

- 小行列では利用率が低い場合がある
- batch sizeを増やすと有利になりやすい
- 同期が必要

同じ表へ混ぜず、deviceごとに結果を分ける。

## 19. memory評価

### パラメータ理論値

$$
\text{parameter bytes}
=
\text{parameter count}
\times
\text{bytes per element}
$$

float32なら1要素4 byteである。

### state_dictサイズ

実際に保存したcheckpointのファイルサイズも測定する。

### GPU memory

forward前にpeak統計をリセットし、実行後にpeak memoryを取得する。

ただし、小さいモデルではCUDA allocatorの単位や既存予約領域の影響が大きい。

パラメータ理論値と実測peakを別々に報告する。

## 20. 学習時間

fine-tuningを比較する場合、推論時間だけでなく学習時間も記録する。

2層化によりパラメータは減るが、

- forwardが2回のLinearになる
- backwardも2層分になる
- optimizer stateが新しい因子へ作られる

ため、単純にパラメータ削減率どおり速くなるとは限らない。

## 22. 理論値と実測値の読み方

### MACs削減率とlatency削減率が近い

対象層が実行時間の大部分を占め、行列積が効率よく実行されている可能性がある。

### MACsは大幅減、latencyは少しだけ改善

他層、kernel起動、memory、DataLoaderが支配的な可能性がある。

### MACsは減ったが遅くなった

2回の小行列積の効率が悪い可能性がある。batch size、rank、CPU/GPUを変えて確認する。

### モデル全体では改善しない

圧縮対象層が総実行時間の小さい割合しか占めていない可能性がある。

## ベンチマークコードでの `_` の使い方

以前の版では、`_` を「捨て変数」と一文でしか説明していなかった。  
添付PDFで扱った使用箇所をすべて整理する。

### `_` はPythonの特別な破棄構文ではない

`_` は普通の変数名である。  
ただしPythonでは、値を受け取る必要はあるが、その後使わない場合に `_` と書く慣習がある。

値は実際には `_` に代入されるため、完全に存在しなくなるわけではない。  
後から参照することも技術的には可能だが、未使用であることを示すため、通常は参照しない。

### 1. ラベルを使わない

```python
images, _ = next(iter(data_loader))
```

DataLoaderは通常、

```python
images, labels
```

のペアを返す。

推論時間測定では正解ラベルを使わないため、

```text
images → 使用する
labels → _ で受け取り、使用しない
```

としている。

### `iter()` と `next()`

```python
iterator = iter(data_loader)
images, labels = next(iterator)
```

- `iter(data_loader)`：DataLoaderを順番に取り出すためのiteratorを作る
- `next(iterator)`：iteratorから次の1バッチを取り出す

したがって、

```python
next(iter(data_loader))
```

は、DataLoaderから最初の1バッチだけを取得する書き方である。

ベンチマークでは同じ入力を繰り返し使い、DataLoaderの読込み時間をforward時間へ混ぜないために1バッチだけ取り出す。

### 2. ループ番号を使わない

```python
for _ in range(warmup):
    model(images)
```

`range(warmup)` は0から `warmup - 1` までの整数を返す。  
今回は何回目かという値を使わず、指定回数だけ繰り返したいため `_` で受ける。

```python
for i in range(warmup):
    ...
```

と書いても動作は同じだが、`i` を使わないなら `_` の方が意図が明確である。

### 3. モデル出力を使わない

```python
_ = model(images)
```

推論時間だけを測る場合、logitsの値そのものは使用しない。  
そのため戻り値を `_` へ代入している。

次のように代入しなくてもforwardは実行される。

```python
model(images)
```

`_ = model(images)` は、「戻り値を意図的に使わない」と明示する書き方である。

### 4. 複数の戻り値の一部だけを使う

rank sweepでは、

```python
_, compressed_macs, compute_reduction = MACs(
    model,
    fc1_rank,
    fc2_rank,
    verbose=False,
)
```

としている。

`MACs()` が3つの値を返すうち、最初のBaseline MACsはループ内で使わないため `_` で受けている。

### `_` と `__init__` は別

```text
_          → 未使用値を受けるための慣習的な変数名
__init__   → Pythonの特殊メソッド名
```

`__init__` の2本のアンダースコアは捨て変数の意味ではない。

## ベンチマーク処理の全体

```python
def benchmark_inference(
    model,
    data_loader,
    device,
    warmup=5,
    repeats=50,
):
    model.eval()

    images, _ = next(iter(data_loader))
    images = images.to(device)

    with torch.inference_mode():
        for _ in range(warmup):
            _ = model(images)

        if device.type == "cuda":
            torch.cuda.synchronize()

        start = time.perf_counter()

        for _ in range(repeats):
            _ = model(images)

        if device.type == "cuda":
            torch.cuda.synchronize()

    elapsed = time.perf_counter() - start
    return elapsed / repeats
```

処理順序：

```text
1. evalモードにする
2. DataLoaderから1バッチだけ取得する
3. deviceへ移す
4. 勾配計算を無効にする
5. warm-upを行う
6. GPU処理を同期する
7. perf_counterで計測開始
8. repeats回forwardする
9. GPU処理を同期する
10. 平均時間を返す
```

今回のMLPにはDropoutとBatchNormがないため、`eval()` によるforward計算の違いはほぼない。  
それでも一般的な推論コードとして `model.eval()` を呼ぶ。

`torch.no_grad()` でもよいが、純粋な推論では `torch.inference_mode()` を使う選択肢もある。

## 表示値の丸め

添付PDFでは `torch.round()` についても確認した。

```python
x = torch.tensor([1.234, 1.235, 1.236])
torch.round(x, decimals=2)
```

PyTorchの `torch.round()` は、ちょうど中間の値で偶数側へ丸める方式を採用する。

```text
2.5 → 2
3.5 → 4
```

これは、常に5を切り上げる意味での四捨五入とは異なる。

実験結果を表示するだけなら、元テンソルそのものを丸めず、f-stringで表示桁数を指定する方がよい。

```python
print(f"{accuracy * 100:.2f}%")
print(f"{latency_ms:.3f} ms/batch")
```

これにより、計算に使う元の精度を保持したまま表示だけを整えられる。

## 22.1 理論MACsが減っても小規模GPU推論が速くならない

低ランク化すると大きな行列積1回が小さい行列積2回になる。
理論MACsは減っても、

- kernel launch overhead
- 小行列でGPUを使い切れない
- 中間テンソルの読み書き
- 追加のlayer呼び出し

などにより、小規模MLPでは実測latencyが改善しないことがある。
推論時間はrank選択の主基準ではなく、理論MACsと分けて補助指標として扱う。

## 23. よくある間違い

### SVD時間を推論時間へ足す

オフライン圧縮コストとオンラインforwardを分ける。

### warm-upなしで初回だけ測る

初期化時間を含み、再現性が低い。

### CUDA同期をしない

実際より短く見える可能性がある。

### batch sizeを記録しない

別実験と比較できない。

### DataLoader時間を含む測定と含まない測定を混ぜる

測定範囲を明記する。

### パラメータ削減率をそのまま速度向上率と呼ぶ

理論値と実測値は別である。

### fc3を最大rankで2層化して圧縮したと思う

rank 10ではパラメータが増える。

## 24. このノートで押さえるポイント

- パラメータ数、MACs、latencyを別々に測る。
- SVD処理時間と圧縮後forward時間を分ける。
- 元LinearのMACsは概ね $D_{in}D_{out}$ である。
- 低ランク2層のMACsは $r(D_{in}+D_{out})$ である。
- 圧縮成立条件は $r < D_{in}D_{out}/(D_{in}+D_{out})$ である。
- 数学的最大rankでも、パラメータ圧縮にならない場合がある。
- `fc3` はrank 10で元より大きくなる。
- warm-up後に複数回測定する。
- GPUでは計測前後に同期する。
- meanとmedianを記録する。
- batch size、device、dtype、測定範囲を併記する。
- 理論MACsが減っても実測latencyが改善するとは限らない。
