# 既知の制約と拡張方針

## 1. 目的

Core API v1は「現在のsrcが完全に一般化されている」という意味ではない。

既存SVD/Tucker実験を安定化した時点のcontractを固定し、未対応範囲は明示したうえでTT/MPS・DMRGへ進む。

このファイルでは、

```text
仕様として意図的に制限しているもの
技術的負債として残しているもの
将来拡張時に壊してはいけないもの
```

を分ける。

---

# 2. Tucker/HOOIは複素dtype未対応

HOSVD/HOOIでは現在factor射影に `U.T` を使う。

複素Tensorでは `U.mH` が必要になるため、分解入口で複素dtypeを明示的にrejectする。

現在の方針：

```text
real Tensor
→ supported

complex Tensor
→ decomposition APIではTypeError
```

複素対応が必要になった場合は、単にguardを外さず、

- transpose / conjugate transpose
- reconstruction
- HOOI projection
- full-rank regression

をまとめて設計・テストしてから対応する。

TT/MPSでも複素対応を導入する場合、既存Tucker APIだけ片側で挙動を変えず、リポジトリ全体のdtype policyとして検討する。

---

# 3. NumPy scalar受理方針は完全統一していない

現在、整数入力の扱いはAPIごとに少し異なる。

例：

```text
SVD rank / max_iter
→ operator.index
→ NumPy integer scalarを受理
→ Tensor scalar拒否

mode validation
→ isinstance(mode, int)
→ NumPy integer scalarを受理しない場合がある

benchmark warmup/repeats
→ operator.index
→ bool拒否
```

Core API v1では、この違いを一括refactorするためだけに既存APIを変更しない。

将来統一する場合は、

```text
Python intのみ
or
__index__対応scalarまで
```

のどちらをリポジトリ標準にするか先に決め、contract testを追加してから行う。

---

# 4. validation helperが複数箇所に存在する

現在、似た処理が、

```text
tensor/validation.py
compression/tucker_validation.py
compression/svd.py
metrics/macs.py
metrics/model_comparison.py
```

に分散している。

主な理由：

```text
compression.hooi
→ metrics
```

という依存が既にあるため、metricsからcompressionへvalidationをimportすると循環importになりやすい。

この重複はprivate implementationであり、Public APIではない。

将来整理するときは、

```text
低位shared validation package
```

を作る等、依存方向を明示してから移動する。

単にDRY化のために循環依存を導入しない。

---

# 5. `collect_compression_metrics` は再走査可能loaderを前提とする

内部で同じloaderを複数回使う。

```text
evaluate
agreement
logits_rmse
```

したがって通常のDataLoaderのようなre-iterable objectを要求する。

一度しか走査できないone-shot iteratorを渡すと、2回目以降がemptyになりうる。

現在はこれを自動cacheする仕様にはしていない。

対応が必要になった場合は、

- 1 passで複数metricsを集計する
- batchをcacheする
- 明示的にfactoryを受ける

等を別途設計する。

TT/MPS追加だけを理由に今すぐ変更しない。

---

# 6. `non_shuffling_loader` は任意DataLoaderの完全cloneではない

現在は、一般的なDataLoader設定のうち主に、

```text
dataset
batch_size
num_workers
collate_fn
pin_memory
timeout
worker関連設定
```

を引き継ぎ、`shuffle=False` のloaderを作る。

custom sampler / custom batch_sampler / 特殊なDataLoader subclass等を完全再現するcontractではない。

既存実験の標準DataLoaderでは問題ない。

---

# 7. model-specific helperは意図的に残す

以下はgeneric library APIではない。

```text
make_one_layer_svd_model
make_two_layer_svd_model
estimate_mlp_macs
estimate_cnn_linear_macs
Fashion-MNIST dataset helpers
```

学習履歴・既存Notebook再現性のためPublic exportしている。

TT/MPSでこれらへ分岐を大量追加して万能関数化しない。

新しい一般化が必要ならgeneric APIを別に追加する。

---

# 8. model architectureは実験fixtureとして固定する

`MNISTMLP`、`FashionMNISTCNN`、`CIFAR10CNN` の既定layer名・default architectureは過去checkpointと圧縮対象名に直結する。

そのためCore API v1中は不用意に変更しない。

例：

```text
CIFAR10CNN.conv2
```

を別名へ変えると、

- checkpoint key
- named layer compression
- Notebook
- results解釈

が同時に壊れる。

新architectureは新classまたは明示的な新optionで追加する。

---

# 9. path utilityは `.git` をproject root markerにする

`find_project_root()` は `.git` の存在を基準にする。

Git checkoutでは扱いやすいが、`.git` を含まないzip展開・一部実行環境ではproject rootを検出できない。

現時点では既存Notebook運用を優先して維持する。

必要になれば、

```text
pyproject.toml
README.md
環境変数
explicit project_root
```

等のmarker追加を別仕様として検討する。

---

# 10. MACsは理論値であり実測速度ではない

既存metricsは、主要な積和演算を理論MACsとして数える。

含めていないものの例：

- bias加算
- activation
- memory transfer
- kernel launch overhead
- framework overhead

そのため、

```text
MACs reduction
!=
latency reduction
```

を設計上の前提とする。

TT/MPSでも理論演算量と実測latencyを分けて記録する。

---

# 11. compressed Conv MACsの出力空間validation

現行 `compressed_conv2d_macs()` は `out_h/out_w > 0` を確認する。

ただし作成時点の実装では、`rank` のように `operator.index()` を通した**厳密な整数型normalizationまでは行っていない**。

したがって「正の値」は検査されるが、API全体として `out_h/out_w` のbool / float受理を完全に統一したcontractにはなっていない。

Core API v1を最終確定するself reviewでは、

```text
out_h/out_wを正整数として厳密に固定するか
現状を既知の制約として維持するか
```

を確認する。

---

# 12. `fit_with_early_stopping` のscalar validation

`fit_with_early_stopping` は現在、

```text
max_epochs
patience
min_delta
```

にHOOI/benchmarkと同程度の統一validation helperを持たない。

既存Notebookから妥当な値を渡すexperiment-support APIとして成立しているが、汎用ライブラリ級の入力検証ではない。

Core API v1ではsignatureと現在のEarly Stopping semanticsを固定し、全面的なvalidation統一は別課題とする。

---

# 13. Public APIの追加と内部refactor

Core API v1固定後も、以下は可能。

### 可能

- private validation helper統合
- HOOI内部の高速化
- memory allocation削減
- type hint改善
- test追加
- optionalな新Public API追加

### 原則不可

- `hooi` のreturn tuple順変更
- `history[0]` の意味変更
- `unfold` のaxis convention変更
- Conv factorizationのfactor順変更
- named compressionをin-place化
- evaluate後にmodel modeを復元しなくする
- existing model classのlayer名変更

---

# 14. TT/MPS追加方針

TT/MPSは既存SVD/Tuckerの延長だが、rank構造は異なる。

既存APIを拡張しすぎず、新しい責務を追加する。

候補：

```text
src/nn_compression/compression/
├─ tensor_train.py
or
├─ tt.py
```

Public API候補：

```text
tt_svd
tt_reconstruct
tt_parameter_count
factorize_linear_tt
```

ただし実装前にNotebookで、

- tensorization
- core shape
- bond dimension
- TT-SVD
- reconstruction
- parameter count

を理解してからsrc化する。

Core API v1へ追加するときは `__all__` とcontract testも同時に更新する。

---

# 15. DMRG追加方針

DMRG-like optimizationは、HOOIで学んだ

```text
initialization
→ local update
→ sweep
→ convergence
```

と概念上つながるが、HOOI APIへDMRG処理を埋め込まない。

DMRGでは、

- MPS/TT表現
- local 1-site / 2-site problem
- environment
- left/right sweep
- truncation
- convergence

が新しい責務になる。

既存 `hooi_sweep()` の意味を一般的な「何でもsweep」へ変更せず、DMRG専用APIを追加する。

---

# 16. breaking changeが必要になった場合

Core API v1の破壊的変更が必要なら、最低限、

```text
1. 変更理由
2. 影響するPublic API
3. 既存Notebookへの影響
4. migration方法
5. contract test更新
6. 設計書更新
```

を残す。

可能なら旧APIをcompatibility wrapperとして一定期間残す。

---

# 17. Core API v1確定条件

この設計書の作成だけでは確定としない。

最終的に、

```text
- Public API一覧と__all__が一致
- 現行srcとsignatureが一致
- testsのcontractと矛盾しない
- ノートの説明と矛盾しない
- freeze前に直すべき小さなcontract gapが残っていない
```

ことをself reviewで確認してから、Core API v1を確定する。
