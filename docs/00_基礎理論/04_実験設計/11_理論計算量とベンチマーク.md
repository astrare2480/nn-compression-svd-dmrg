# 理論計算量と実測時間

## サマリー

SVD圧縮では、次の3つのコストを分ける。

1. モデルに保存するパラメータ数
2. 圧縮後forwardの理論演算回数
3. 実際の推論時間

さらに、学習済み重みにSVDを1回かける前処理コストも別に存在する。

```text
SVDを計算する時間
≠
圧縮後モデルを推論する時間
```

NN圧縮の主目的が推論モデルの軽量化なら、報告すべき中心は、

- 圧縮後パラメータ数
- 圧縮後MACs
- 圧縮後実測latency

である。

SVD処理時間は、圧縮を何回実施するか、モデルを何回推論するかによって重要度が変わる。

---

## 対応コード

現在の層単位MACsは、

```text
src/nn_compression/metrics/macs.py
```

へ分離している。

```python
from nn_compression.metrics import (
    linear_macs,
    compressed_linear_macs,
    conv2d_macs,
    compressed_conv2d_macs,
)
```

モデル全体の集計は、モデル構造固有として別ファイルに置く。

```text
src/nn_compression/metrics/mlp_macs.py
src/nn_compression/metrics/cnn_macs.py
```

CNN側の公開関数：

```text
estimate_cnn_linear_macs
estimate_cnn_conv2_macs
estimate_cnn_macs
```

- `estimate_cnn_linear_macs`：02 / 03と同じく `fc1 + fc2` のLinear部だけを比較
- `estimate_cnn_conv2_macs`：04と同じく `conv2` 単体を比較
- `estimate_cnn_macs`：05で `conv1 + conv2 + fc1 + fc2` のモデル全体を比較

推論時間の共通実装は、

```text
src/nn_compression/metrics/model_comparison.py
```

の `benchmark_inference()` / `benchmark_inference_print()` を正本とする。

現行contractでは、

```text
warmup  : boolではない0以上の整数
repeats : boolではない1以上の整数
```

を要求し、比較では同じ `input_batch` を共有する。測定のために一時的に `eval()` へ切り替えても、終了時にはrootだけでなく全submoduleの `.training` 状態を個別に復元する。

> [!important]
> `compute_reduction` を比較するときは**何を分母にした削減率か**を揃える。  
> `conv2` 単体の46%削減と、CNN全体の46%削減は同じ意味ではない。

## 1. 元Linear層のパラメータ数

```python
nn.Linear(
    in_features=D_in,
    out_features=D_out,
    bias=True,
)
```

の重み数は、

$$
D_{\mathrm{out}}D_{\mathrm{in}}
$$

bias数は、

$$
D_{\mathrm{out}}
$$

である。

総パラメータ数は、

$$
P_{\mathrm{original}}
=
D_{\mathrm{out}}D_{\mathrm{in}}
+
D_{\mathrm{out}}
$$

となる。

---

## 2. 低ランク2層のパラメータ数

前段：

```text
Linear(D_in, r, bias=False)
```

後段：

```text
Linear(r, D_out, bias=True)
```

なので、

$$
P_{\mathrm{lowrank}}
=
rD_{\mathrm{in}}
+
rD_{\mathrm{out}}
+
D_{\mathrm{out}}
$$

である。

bias数は元と同じため、圧縮成立条件では相殺される。

$$
P_{\mathrm{lowrank}}
<
P_{\mathrm{original}}
$$

より、

$$
r
<
\frac{D_{\mathrm{in}}D_{\mathrm{out}}}{D_{\mathrm{in}}+D_{\mathrm{out}}}
$$

となる。

---

## 3. rank上限と圧縮成立rank

| 層 | shape | 数学的最大rank | パラメータが減るrank |
|---|---:|---:|---:|
| `fc1` | 512×784 | 512 | 309以下 |
| `fc2` | 256×512 | 256 | 170以下 |
| `fc3` | 10×256 | 10 | 9以下 |

### `fc3` の重要点

`fc3` ではrank 10はSVDとして有効である。

しかし、

```text
元のパラメータ数 = 2,570
rank 10の2層化  = 2,670
```

となり、100個増える。

したがって、最大rankと圧縮になるrankは別である。

## 7. 元Linear層のMACs

1サンプルに対する `Linear(D_in, D_out)` のMACsは概ね、

$$
\operatorname{MACs}_{\mathrm{original}}=D_{\mathrm{in}}D_{\mathrm{out}}
$$

である。

bias加算は別途存在するが、主要な行列積と比べて小さいため、最初の比較では除外してよい。

---

## 8. 低ランク2層のMACs

前段は $D_{\mathrm{in}}r$、後段は $rD_{\mathrm{out}}$ なので、

$$
\operatorname{MACs}_{\mathrm{lowrank}}
=r(D_{\mathrm{in}}+D_{\mathrm{out}})
$$

となる。

batch size $N$ なら、元は

$$
ND_{\mathrm{in}}D_{\mathrm{out}}
$$

圧縮後は

$$
Nr(D_{\mathrm{in}}+D_{\mathrm{out}})
$$

である。

---

## 9. MACsとFLOPs

1 MACを「1回の乗算 + 1回の加算」と数える場合、2 FLOPsとする流儀がある。

$$
\operatorname{FLOPs}\approx2\times\operatorname{MACs}
$$

一方、資料によってはMACを1演算として報告する。

比較では、

- MACsなのか
- FLOPsなのか
- bias加算を含むか
- activationを含むか

を明記する。

このノートでは、Linear層の行列積とConv2dの畳み込み積和をMACsで比較する。

---

## 10. パラメータ数とMACsが似た式になる理由

密なLinear層では、各weightが1回のforwardで概ね1回使われる。

そのため、1サンプル当たりでは、

```text
重み数 ≈ 乗算回数
```

となる。

しかし実測時間は、重み数やMACsだけで決まらない。

### 10.1 パラメータ数削減とMACs削減が一致する特殊ケース

Linear層だけを2因子へ置換し、bias総数が圧縮前後で変わらない場合、モデル全体について、

```text
parameters = MACs + bias総数
```

となることがある。

このとき `parameters < baseline_parameters` と `compute_reduction > 0` は数学的に同じ候補集合を表す。

ただし一般則ではない。畳み込み、BatchNorm、Embedding、追加bias、非線形層、その他の構造が入れば同値とは限らない。

Fashion-MNISTの `784 -> 512 -> 256 -> 10` MLPでは、圧縮前後でbias総数が778のままなので、この等価性が成立した。

### 10.2 Conv2dのパラメータ数

`groups=1` のConv2dでは、weight数は

$$
C_{\mathrm{out}}C_{\mathrm{in}}K_hK_w
$$

である。biasがあれば $C_{\mathrm{out}}$ を加える。

一般のgrouped convolutionではPyTorchのweight shapeが

```text
(C_out, C_in / groups, K_h, K_w)
```

なので、weight数は

$$
C_{\mathrm{out}}\frac{C_{\mathrm{in}}}{\mathrm{groups}}K_hK_w
$$

である。

現在の `conv2d_macs()` は `conv.weight.shape[1]` をそのまま使う。これは既に `C_in / groups` なので、さらに `groups` で割らない。

### 10.3 Conv2dのMACs

1サンプルで、出力空間サイズを $H_{\mathrm{out}}\times W_{\mathrm{out}}$ とする。

`groups=1` では、

$$
\operatorname{MACs}_{\mathrm{Conv}}
=H_{\mathrm{out}}W_{\mathrm{out}}C_{\mathrm{out}}C_{\mathrm{in}}K_hK_w
$$

一般のgroupsでは、

$$
\operatorname{MACs}_{\mathrm{Conv}}
=H_{\mathrm{out}}W_{\mathrm{out}}C_{\mathrm{out}}\frac{C_{\mathrm{in}}}{\mathrm{groups}}K_hK_w
$$

となる。

### 10.4 低ランク2層ConvのMACs

`groups=1` の元Convを、

```text
Conv(C_in → r, K_h×K_w)
↓
Conv(r → C_out, 1×1)
```

へ分解する。

合計は、

$$
\boxed{
\operatorname{MACs}_{\mathrm{factorized\ Conv}}
=H_{\mathrm{out}}W_{\mathrm{out}}r(C_{\mathrm{in}}K_hK_w+C_{\mathrm{out}})
}
$$

となる。

現行 `compressed_conv2d_macs()` は `groups=1` のみを対象とし、rankをSVD側と同じくbool拒否・

$$
1\le r\le\min(C_{\mathrm{out}},C_{\mathrm{in}}K_hK_w)
$$

で検証する。`out_h / out_w` も正の値を要求する。

### 10.5 FashionMNISTCNNのMACs検算例

現在の小型CNNでは、1サンプルの主要MACsは次になる。

| 層 | MACs |
|---|---:|
| `conv1` | 225,792 |
| `conv2` | 3,612,672 |
| `fc1` | 401,408 |
| `fc2` | 1,280 |
| **合計** | **4,241,152** |

`conv2 rank = 28`, `fc1 rank = 24` とすると、

| 層 | 圧縮後MACs |
|---|---:|
| `conv1` | 225,792 |
| factorized `conv2` | 1,931,776 |
| factorized `fc1` | 78,336 |
| `fc2` | 1,280 |
| **合計** | **2,237,184** |

となり、

$$
1-\frac{2{,}237{,}184}{4{,}241{,}152}\approx47.25\%
$$

である。

### 10.6 パラメータ削減とMACs削減の役割差

今回のCNNでは、

```text
fc1
→ パラメータ数の大部分を持つ

conv2
→ パラメータ数はfc1より少ない
→ しかし空間上で繰り返し使うためMACsが大きい
```

という構造になっている。

したがって、Linear SVDは主にモデルサイズ削減、Conv SVDは主に畳み込み演算量削減へ効く傾向がある。ただし各モデルの層構成とshapeで判断する。

### 10.7 削減率の分母を必ず確認する

同じ `compute_reduction` でも、実験によって分母が異なる場合がある。

```text
02 / 03 → fc1 + fc2 のLinear部
04      → conv2単体
05      → CNN全体
```

CSVやグラフを横比較するときは、何のMACsをbaselineとしているかを明示する。

---

## 11. パラメータ数が減っても必ず速くならない理由

元の1回の大きな行列積が、2回の小さい行列積へ変わる。

実測時間には、次が影響する。

- kernel起動回数
- 小行列のGPU利用効率
- メモリアクセス
- batch size
- CPUのBLAS実装
- GPUの種類
- dtype
- Python overhead
- cache
- 非同期実行
- 他の層の割合

小さいモデルでは、理論MACsが減っても層分割のオーバーヘッドで速くならない可能性がある。

---

## 12. SVD自体の計算コスト

SVDは無料ではない。しかしpost-training圧縮では通常、

```text
学習後に1回SVD
↓
圧縮モデルを多数回推論
```

となるため、SVD時間は一度だけ支払うオフラインコストである。

- `svd_decomposition_time_ms`
- `inference_latency_ms`

を別々に記録し、SVD時間をforward latencyへ含めない。

---

## 13. 実測時間の対象

少なくとも次を分ける。

### 1バッチlatency

決めたbatch sizeの入力を1回forwardする時間。

### 1サンプル換算

$$
\frac{\text{batch latency}}{\text{batch size}}
$$

ただしbatch処理は完全な線形スケールではないので、batch sizeも必ず併記する。

### dataset throughput

$$
\frac{\text{処理サンプル数}}{\text{総時間}}
$$

としてsamples/sを出す。

---

## 14. ベンチマーク前の条件

- `model.eval()`
- `torch.no_grad()` または `torch.inference_mode()`
- 同じdevice
- 同じdtype
- 同じinput shape
- 同じbatch size
- 同じwarmup / repeats
- **baseline / compressedで同じinput batch**
- DataLoader時間を含むか明記

純粋なmodel forwardを測るなら、入力Tensorを事前にdeviceへ置き、DataLoaderと転送時間を除外する。

現行 `benchmark_inference()` では `input_batch` を直接渡せる。baselineとcompressedの比較では、同じTensorを一度取り出して両方へ渡し、DataLoader Generatorやshuffleの消費差を測定条件へ混ぜない。

shuffle付きDataLoaderから比較用batchを自動取得するとGeneratorを消費するため、`take_inference_batch()` はそのケースを拒否する。必要なら明示的に同じ `input_batch` を渡す。

また、ベンチマークのために `model.eval()` を呼んでも、処理後にはroot + 全submoduleの `.training` 状態を元へ戻す。frozen BatchNormのような個別状態を壊さない。

---

## 15. warm-upと回数contract

初回実行には、

- CUDA context初期化
- kernel選択
- memory allocation
- cache

などが含まれるため、計測前に複数回forwardを実行する。

```text
warm-up 10〜50回
measurement 100回以上
```

は小さいモデルの初期目安であり、実際の回数は環境に応じて調整する。

現行srcでは入力ミスを早期に止めるため、

```text
warmup  >= 0
repeats >= 1
```

を要求し、boolやfloatを整数回数として黙って受理しない。

---

## 16. CUDA同期

CUDA演算は非同期である。

Python側の時計だけを見ると、GPU処理が完了する前に時間を取得する可能性がある。

現行srcでは対象deviceがCUDAなら、計測の前後で

```python
torch.cuda.synchronize(device)
```

を呼ぶ。CPU測定では同期しない。

---

## 17. 平均・中央値・分散

latencyはOS割り込みや他プロセスによって外れ値を含む。

記録候補：

- mean
- median
- standard deviation
- minimum
- p90
- p95

現行 `benchmark_inference()` は指定回数の平均 `time_s` を返す。medianやpercentileが必要なら、別途各repeatの時間を保存するベンチマークを用意する。

---

## 18. CPUとGPUを分ける

CPUとGPUでは最適なrankやbatch sizeが異なる可能性がある。同じ表へ混ぜずdeviceごとに結果を分ける。

### CPU

- 小さいモデルでも比較しやすい
- スレッド数の影響が大きい
- BLAS実装の影響がある

### GPU

- 小行列では利用率が低い場合がある
- batch sizeを増やすと有利になりやすい
- 同期が必要

---

## 19. memory評価

### パラメータ理論値

$$
\text{parameter bytes}
=\text{parameter count}\times\text{bytes per element}
$$

float32なら1要素4 byteである。

state_dictサイズやGPU peak memoryは理論パラメータ量と別々に報告する。

---

## 20. 学習時間

fine-tuningを比較する場合、推論時間だけでなく学習時間も記録する。

低rank化によりパラメータは減っても、forward/backwardの層数やoptimizer stateが変わるため、単純に削減率どおり速くなるとは限らない。

## 22. 理論値と実測値の読み方

### MACs削減率とlatency削減率が近い

対象層が実行時間の大部分を占め、行列積が効率よく実行されている可能性がある。

### MACsは大幅減、latencyは少しだけ改善

他層、kernel起動、memory等が支配的な可能性がある。

### MACsは減ったが遅くなった

小さい演算へ分割した効率が悪い可能性がある。batch size、rank、CPU/GPUを変えて確認する。

## ベンチマークコードでの `_` の使い方

以前の版では、`_` を「捨て変数」と一文でしか説明していなかったため、使用箇所を整理する。

### `_` はPythonの特別な破棄構文ではない

`_` は普通の変数名である。ただしPythonでは、値を受け取る必要はあるが、その後使わない場合に `_` と書く慣習がある。

値は実際には `_` に代入されるため、完全に存在しなくなるわけではない。後から参照することも技術的には可能だが、未使用であることを示すため通常は参照しない。

### 1. ラベルを使わない

```python
images, _ = next(iter(data_loader))
```

DataLoaderが `(images, labels)` を返す場合、推論時間測定ではlabelを使わないため `_` で受ける。

ただし現行の比較ベンチマークでは、baseline / compressedで同じ入力を保証するため、loaderから都度取るより一度取得した `input_batch` を共有する方を優先する。

### `iter()` と `next()`

```python
iterator = iter(data_loader)
images, labels = next(iterator)
```

- `iter(data_loader)`：iteratorを作る
- `next(iterator)`：次の1バッチを取り出す

`next(iter(data_loader))` は最初の1バッチだけを取得する書き方である。

### 2. ループ番号を使わない

```python
for _ in range(warmup):
    _ = model(images)
```

何回目かという値を使わず、指定回数だけ繰り返すので `_` を使う。

### 3. モデル出力を使わない

```python
_ = model(images)
```

推論時間だけを測る場合、logits自体は使用しない。「戻り値を意図的に使わない」ことを明示する書き方である。

### 4. 複数の戻り値の一部だけを使う

```python
_, compressed_macs, compute_reduction = MACs(...)
```

3つの戻り値のうち最初を使わないため `_` で受ける。

### `_` と `__init__` は別

```text
_        → 未使用値を受ける慣習的な変数名
__init__ → Pythonの特殊メソッド名
```

## 現行ベンチマーク処理の使い方

現行srcを使うときは、比較対象へ同じ入力Tensorを渡す。

```python
from nn_compression.metrics import benchmark_inference, take_inference_batch

input_batch = take_inference_batch(eval_loader)

baseline_time = benchmark_inference(
    baseline_model,
    device=device,
    warmup=20,
    repeats=2000,
    input_batch=input_batch,
)

compressed_time = benchmark_inference(
    compressed_model,
    device=device,
    warmup=20,
    repeats=2000,
    input_batch=input_batch,
)
```

内部の概念的な処理順序は、

```text
1. warmup / repeatsをvalidation
2. 同じinput batchをdeviceへ移す
3. root + 全submoduleのtraining状態を保存
4. evalモードにする
5. warm-up
6. CUDAなら同期
7. perf_counterで計測開始
8. repeats回forward
9. CUDAなら同期
10. 平均時間を計算
11. 全moduleのtraining状態を個別に復元
```

となる。

`return_details=True` なら、時間だけでなく `batch_size / input_shape / warmup / repeats` も返せる。

## 表示値の丸め

```python
x = torch.tensor([1.234, 1.235, 1.236])
torch.round(x, decimals=2)
```

PyTorchの `torch.round()` は、ちょうど中間の値で偶数側へ丸める方式を採用する。

```text
2.5 → 2
3.5 → 4
```

実験結果を表示するだけなら、元テンソルそのものを丸めず、f-stringで表示桁数を指定する方がよい。

```python
print(f"{accuracy * 100:.2f}%")
print(f"{latency_ms:.3f} ms/batch")
```

## 22.1 理論MACsが減っても小規模GPU推論が速くならない

低ランク化すると大きな演算1回が小さい演算複数回になる。

理論MACsは減っても、

- kernel launch overhead
- 小行列でGPUを使い切れない
- 中間テンソルの読み書き
- 追加のlayer呼び出し

などにより、実測latencyが改善しないことがある。

推論時間はrank選択の主基準ではなく、理論MACsと分けて補助指標として扱う。

## 23. よくある間違い

### SVD時間を推論時間へ足す

オフライン圧縮コストとオンラインforwardを分ける。

### warm-upなしで初回だけ測る

初期化時間を含み、再現性が低い。

### CUDA同期をしない

実際より短く見える可能性がある。

### baseline / compressedで別batchを使う

入力差をモデル差として測ってしまう。同じ `input_batch` を共有する。

### `warmup=False` や `repeats=1.5` を回数として扱う

現行srcではboolや非整数を拒否する。

### batch sizeを記録しない

別実験と比較できない。

### DataLoader時間を含む測定と含まない測定を混ぜる

測定範囲を明記する。

### パラメータ削減率をそのまま速度向上率と呼ぶ

理論値と実測値は別である。

### fc3を最大rankで2層化して圧縮したと思う

rank 10ではパラメータが増える。

## 24. このノートで押さえるポイント

- パラメータ数、MACs、latencyを別々に測る。
- SVD処理時間と圧縮後forward時間を分ける。
- 元LinearのMACsは概ね $D_{in}D_{out}$ である。
- 低ランク2層のMACsは $r(D_{in}+D_{out})$ である。
- 圧縮成立条件は $r < D_{in}D_{out}/(D_{in}+D_{out})$ である。
- 数学的最大rankでも、パラメータ圧縮にならない場合がある。
- `fc3` はrank 10で元より大きくなる。
- warm-up後に複数回測定する。
- baseline / compressedではsame input batchを使う。
- `warmup / repeats` は整数contractを守る。
- GPUでは対象deviceを同期する。
- ベンチマーク前後で既存のtrain/eval状態を壊さない。
- batch size、device、dtype、測定範囲を併記する。
- 理論MACsが減っても実測latencyが改善するとは限らない。
