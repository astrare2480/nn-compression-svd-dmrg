## 2. srcとNotebookの責務

このリポジトリは学習用でもあるため、Notebookからすべての処理を消してsrcへ移す設計にはしない。

```text
Notebook
→ 数式・shape・途中結果を確認する
→ 自作実装の学習履歴を残す
→ 実験固有の候補選択・表・グラフを持つ

src
→ 複数Notebookから再利用する処理
→ public contractを持つ処理
→ validation・device/dtype・状態管理を一元化する処理
```

実験固有の最終rankやCSV名をsrcへ埋め込まない。

---

## 3. パッケージ責務

### `tensor`

分解手法に依存しないmode-nテンソル演算。

```text
unfold
fold
mode_dot
```

Tuckerだけでなく、今後のTT/MPS等で再利用できる下位層として扱う。

`tensor` は `compression` に依存しない。

### `compression`

NN weightの低rank分解・層置換。

```text
SVD
Linear SVD
Conv2d SVD
named layer置換
rank sweep
HOSVD / Tucker
HOOI
Tucker-2 Conv
```

数学アルゴリズムとPyTorch Module構築の境界を分ける。

### `training`

学習・評価ループ。

```text
train_one_epoch
evaluate
fit_with_early_stopping
non_shuffling_loader
```

圧縮方式そのものには依存しない。

### `metrics`

圧縮前後の評価・理論計算量。

```text
parameter count
accuracy drop
agreement
logits RMSE
latency benchmark
MACs
relative Frobenius error
```

分解アルゴリズムとは別責務とする。

### `selection`

実験候補のPareto / knee選択。

数学的圧縮アルゴリズムから分離し、pandas / NumPyを使う小規模な候補処理を担当する。

### `datasets`

Dataset取得・再現可能な分割・DataLoader作成。

### `models`

実験で再利用するbaseline model定義。

### `utils`

他の責務に属しにくい小さな共通処理。

```text
named module get/set
project root / experiment path
seed / torch.Generator
```

## 4. 依存方向

主要な依存関係は概念的に次の通り。

```text
utils ───────────────┐
  ↑                  │
  ├─ datasets        │
  ├─ compression     │
  └─ metrics         │
                     │
tensor ──→ compression
              │
              ├─→ metrics   # HOOIのrelative error、rank sweepの評価
              └─→ utils

training ──→ metrics.model_comparison

models / selection
→ 基本的に他の高位パッケージへ依存しない
```

特に重要なのは、現在 `compression.hooi` が `metrics.relative_frobenius_error` を利用するため、**metrics側からcompressionをimportしない**ことである。

この依存方向を壊すと循環importになりやすい。

そのため現在、整数validationの小さなロジックが

```text
compression.svd
metrics.macs
metrics.model_comparison
```

に一部分散している。これは無条件に重複削除するのではなく、依存方向を保ったまま共通化できる場所が決まったときに整理する。

---

## 5. 数学APIとModule構築APIを分ける

例としてTucker-2では、

```text
weight Tensor
→ tucker2_decompose_conv_weight / tucker2_hooi
→ core / factors
```

と、

```text
Conv2d + core / factors
→ build_tucker2_conv_from_components
→ nn.Sequential
```

を分けている。

この分離により、

- 分解手法だけ比較する
- HOSVDとHOOIで同じModule構築を使う
- Tensor-level APIではautograd graphを保持する
- 学習用Module構築時だけ元モデルとのgraphを切る

という責務分離ができる。

SVDでも同様に、

```text
truncated_svd
→ U, S, Vh

factorize_linear_layer / factorize_conv2d_layer
→ 新しいModule
```

と分ける。

---

## 6. 元モデルを破壊しない

モデル単位の圧縮APIでは、baseline modelを直接書き換えない。

```text
baseline
→ deepcopy
→ copy側だけlayer置換
→ compressed model
```

対象：

- `factorize_named_linear`
- `factorize_named_conv2d`
- `factorize_named_layers`
- `make_one_layer_svd_model`
- `make_two_layer_svd_model`
- rank sweep内candidate

Fine-tuning後もbaselineとParameter object / storageを共有しないことをcontractとする。

層単体を受け取る `factorize_linear_layer` / `factorize_conv2d_layer` / `build_tucker2_conv` は新しいModuleを返し、入力layer自体を置換しない。

---

## 7. device / dtype / trainability

NN Moduleを新規構築する圧縮APIでは、原則として元layerの

```text
device
dtype
requires_grad
bias有無
```

を維持する。

Conv2dではさらに、意味を変えないため元の

```text
stride
padding
dilation
padding_mode
```

を空間演算を担当するfactor/core layerへ引き継ぐ。

現在のConv SVD / Tucker-2は `groups=1` の通常Conv2dのみ対応する。

---

## 8. validationはPublic API境界で行う

invalidな入力をPyTorch内部の偶発的な例外まで流さない。

現在の主なcontract：

```text
rank
→ bool拒否
→ 整数scalar
→ 1 <= rank <= 数学的最大rank

mode
→ bool拒否
→ int
→ 0 <= mode < ndim

Tensor shape
→ ndim >= 2
→ dimension > 0

Tucker ranks
→ Mapping
→ {mode: rank}
→ HOOIでは空Mapping不可
```

HOSVD/HOOI分解は現行実装では実数Tensorのみを正式サポートする。

---

## 9. train/eval状態を壊さない

評価・比較・benchmarkは一時的に `eval()` を使うが、呼び出し元のmodel状態を副作用として変えない。

rootの `model.training` だけでなく、全submoduleの `.training` を個別に保存・復元する。

これにより、

```text
root = train
BatchNormだけ = eval
```

のようなモデルでも評価後に元の状態へ戻る。

一方 `train_one_epoch()` は学習APIなので `model.train()` に切り替え、その状態を維持する。

---

## 10. DataLoaderと乱数状態

候補比較でshuffle付きDataLoaderのGeneratorを不用意に進めない。

```text
training loader
→ shuffle=True
→ 学習専用

train evaluation loader
→ shuffle=False
→ train metric再評価用
```

latency benchmarkでもbaselineとcompressedに同一の `input_batch` を使う。

`take_inference_batch()` は `RandomSampler` を検出した場合、shuffle Generator消費を避けるため明示的に拒否する。

## 11. test suiteの位置付け

Core API v1は設計書だけで固定しない。

```text
tests/test_api_contracts.py
tests/test_contract_validation.py
tests/test_generic_src.py
tests/test_cnn_src_refactor.py
tests/test_tucker_src.py
tests/test_hooi.py
tests/test_conv_tucker.py
...
```

が実行可能なcontractとして機能する。

作成時点の全suite：

```text
252 passed
0 failed
```

Public APIを変更するときは、対応するcontract testとこの設計書の両方を更新する。

---

## 12. 今後の基本原則

TT/MPS・DMRG追加時は、

```text
既存APIを修正して新方式へ合わせる
```

より、

```text
既存のtensor / metrics / training契約を再利用
+
新しいcompression / tensor-network APIを追加
```

を優先する。

既存SVD/Tucker実験の再現性を守りながら、新しい表現を積み重ねる設計とする。
